# PRD.md — Verified

## 1. Product Vision

AI agents increasingly take real-world actions — calling APIs, writing to databases, executing SQL, triggering payments, invoking other agents — based on structured output (JSON, function-call arguments, SQL) generated by LLMs. That output is frequently malformed, mistyped, unsafe, or subtly wrong, and today most systems either trust it blindly or rely on ad hoc, per-integration validation.

**Verified** is a local-first verification layer that sits between an AI agent's generated structured output and the system that would execute it. It runs on a Jetson Nano at the edge, close to the agent, and enforces a single invariant:

> **No valid proof, no execution.**

Verified performs deterministic, local checks first (schema validity, type correctness, syntax, SQL safety, privacy policy compliance) and repairs what it safely can without ever sending data off-device. When a problem cannot be resolved deterministically — for example, a semantically ambiguous repair that requires model-level judgment — Verified escalates to a paid, pay-per-call **semantic-repair API**, metered and settled using the **x402** payment protocol on **Algorand**, brokered through the **GoPlausible AVM facilitator**. Every repaired output is re-validated before it is trusted. Every verification outcome — pass, repair, or reject — produces a cryptographically bound **verification receipt**, and receipts are periodically anchored on Algorand via a Merkle root for tamper-evident auditability, without ever putting raw payloads on-chain.

## 2. Problem Statement

- AI agent output is structurally and semantically unreliable, but is often executed (SQL run, API called, transaction submitted) without independent verification.
- Existing validation approaches are either: (a) purely local and unable to fix anything requiring semantic judgment, or (b) fully cloud-based, sending every payload to a paid LLM regardless of whether local checks would have sufficed — expensive and privacy-hostile.
- There is no standard, portable mechanism for an execution system to demand cryptographic proof that a given output was verified before acting on it.
- There is no tamper-evident audit trail connecting a specific AI output, the schema/policy it was checked against, the repair applied (if any), and the outcome.

## 3. Goals

- Verify structured AI output (JSON, SQL, function-call arguments) locally, deterministically, and by default without network calls.
- Repair safely-fixable issues locally (e.g., trivial type coercion, whitespace/formatting, missing-but-defaultable fields — see ARCHITECTURE.md for exact deterministic-repair scope) without invoking the paid API.
- Escalate only the subset of failures that require semantic repair to a paid API, gated by x402 payment on Algorand.
- Re-validate all repaired output before it is considered trustworthy.
- Produce a verification receipt for every request that downstream systems can require before executing on the output.
- Provide tamper-evident auditability of verification history via periodic Merkle-root anchoring on Algorand, without exposing raw payload contents on-chain.
- Demonstrate the full local → escalate → pay (x402/Algorand) → repair → re-verify → receipt → anchor loop as a coherent, working hackathon MVP.

## 4. Non-Goals

- Verified is **not** a general-purpose LLM output "quality" or hallucination-detection product for prose/creative text.
- Verified does **not** execute the agent's action itself (it produces a verification receipt/proof; execution is the responsibility of a downstream consumer that checks the receipt).
- Verified does **not** attempt to guarantee semantic *correctness* of an output against real-world facts — only structural validity, type/syntax correctness, safety-policy compliance, and (post-repair) re-validated consistency.
- Verified is not designed, in its MVP, to be a general blockchain oracle or a general-purpose payment gateway; x402/Algorand usage is scoped strictly to (a) metering semantic-repair calls and (b) anchoring audit evidence.
- Verified does not store or manage the agent's private keys or wallet infrastructure; it consumes a payment credential presented by the client (see DESIGN.md, DATA_MODEL.md — exact custody model TBD).

## 5. Target Users

- **AI agent developers / orchestration frameworks** who need an execution-gating checkpoint before an agent's structured output is acted on.
- **Hackathon judges / evaluators** assessing a working demonstration of x402 + Algorand + edge AI verification.
- **Systems that must audit AI-driven actions after the fact** (e.g., an operator who later needs to prove what was verified and when).

## 6. Core Capabilities

1. **Structured-output validation**
   - JSON Schema (or equivalent — TBD, see ARCHITECTURE.md) conformance checking.
   - Type checking of fields against declared/expected types.
   - Syntax checking for structured outputs that are themselves code-like (e.g., SQL statements, function-call argument sets).
   - SQL safety checks (e.g., detecting unsafe statement classes — exact rule set TBD; see THREAT_MODEL.md and ARCHITECTURE.md).
   - Privacy filtering: detecting payload content that must not be sent off-device before any escalation decision is made.
2. **Deterministic local repair**
   - A bounded set of safe, rule-based repairs applied without model inference or network access.
3. **Semantic-repair escalation**
   - Escalation of unresolved issues to a paid semantic-repair API when local repair cannot safely resolve them.
   - x402-based payment flow (HTTP 402 challenge → signed `X-PAYMENT` → facilitator verification/settlement) gating access to that API.
4. **Re-validation after repair**
   - Any repaired output (local or semantic) is re-run through the validation pipeline before being considered pass/fail.
5. **Verification receipts**
   - A structured, cryptographically hashed record of the verification outcome for a given request, suitable for a downstream system to check before executing.
6. **Tamper-evident audit anchoring**
   - Local verification records, periodically summarized into a Merkle tree, with the root anchored on Algorand.

## 7. User Flows

### 7.1 Local-only pass (happy path, no payment)
1. Agent submits structured output + schema/policy reference to Verified.
2. Verified runs schema/type/syntax/SQL-safety/privacy checks locally.
3. Output passes all checks (or is deterministically repaired and re-validated successfully).
4. Verified issues a verification receipt marked `verified`.
5. Downstream system checks the receipt and proceeds with execution.

### 7.2 Escalated semantic repair (paid path)
1. Agent submits structured output; local validation fails in a way deterministic repair cannot resolve.
2. Verified determines semantic repair is required and returns an HTTP 402 challenge for the escalation call.
3. Agent (or its wallet-holding client) presents a signed `X-PAYMENT` per x402.
4. GoPlausible AVM facilitator verifies and settles payment on Algorand.
5. Verified forwards the (privacy-filtered) payload to the semantic-repair API.
6. Repaired output is returned and re-validated locally.
7. If re-validation passes, Verified issues a `verified (repaired)` receipt; if it still fails, Verified issues a `rejected` receipt.
8. Downstream system checks the receipt; execution proceeds only on a valid, passing receipt.

### 7.3 Rejection (fail-closed path)
1. Local validation fails.
2. Either semantic repair is not warranted/available, or semantic repair is attempted and re-validation still fails, or payment cannot be verified/settled.
3. Verified issues a `rejected` receipt with reasons.
4. Downstream system is expected to refuse execution absent a valid `verified` receipt (fail-closed — see Architecture Principle 8).

### 7.4 Audit / dispute flow
1. An operator later needs to confirm whether a specific output was verified and what happened to it.
2. Operator retrieves the local verification record and receipt for that request.
3. Operator confirms the receipt's hash is included in a Merkle tree whose root was anchored on Algorand at a given time, proving the record has not been altered since anchoring.

## 8. Functional Requirements

- FR1: Verified MUST accept a structured-output verification request consisting of the output to verify, a reference to the applicable schema/policy, and request metadata (see DATA_MODEL.md).
- FR2: Verified MUST perform schema validation, type checking, syntax checking, SQL safety checks, and privacy filtering locally before any network call is considered.
- FR3: Verified MUST attempt deterministic repair only within a clearly bounded, enumerable rule set (no model inference for deterministic repair).
- FR4: Verified MUST NOT call the semantic-repair API unless local validation/repair could not resolve all detected issues.
- FR5: Verified MUST gate every semantic-repair API call behind a valid x402 payment (HTTP 402 → `X-PAYMENT` → facilitator verification/settlement) before forwarding payload data.
- FR6: Verified MUST re-validate any output returned by the semantic-repair API using the same validation pipeline used for the original output.
- FR7: Verified MUST produce a verification receipt for every request, regardless of outcome (verified / verified-repaired / rejected).
- FR8: Each verification receipt MUST include cryptographic hashes binding it to the output, schema/policy, and repair information used to produce it.
- FR9: Verified MUST periodically compute a Merkle root over a batch of local verification records and anchor that root on Algorand.
- FR10: Verified MUST NOT place raw payload content on-chain, at any point.
- FR11: Verified MUST apply privacy filtering *before* any payload leaves the local environment for escalation.
- FR12: Verified MUST fail closed: any unresolved uncertainty, invalid payment, or invalid proof MUST NOT result in a `verified` receipt.

## 9. Non-Functional Requirements

- **Privacy:** confidential payload content must not leave the Jetson unless escalation is strictly necessary, and only after privacy filtering.
- **Integrity:** receipts and audit records must be tamper-evident; any post-hoc modification must be detectable against the anchored Merkle root.
- **Determinism/predictability:** local validation and deterministic repair behavior must be reproducible given the same input, schema, and validator version.
- **Auditability:** it must be possible to reconstruct, for any past request, what was checked, what was repaired, and what the outcome was.
- **Fail-closed behavior:** system faults (network unavailability, facilitator failure, payment failure) must default to rejection, never to silent pass-through.
- **Hackathon-appropriate reliability:** the MVP must run a full end-to-end demo reliably on a single Jetson Nano without requiring production-grade high availability.
- Performance targets, throughput numbers, and latency budgets are **TBD** — no numbers are assumed at this stage (see ARCHITECTURE.md for discussion of what needs to be benchmarked).

## 10. MVP Scope

Included:
- Local validation pipeline: schema, type, syntax, SQL safety, privacy filtering (see ARCHITECTURE.md for exact deterministic-repair rule set — TBD list to be finalized during implementation).
- Deterministic repair for a small, explicitly enumerated set of safe cases.
- Semantic-repair escalation path with x402 HTTP 402 challenge/response.
- Integration with the GoPlausible AVM facilitator for Algorand-based payment verification/settlement.
- Re-validation of repaired output.
- Verification receipt generation with hashing.
- Local verification record store.
- Periodic Merkle-root computation and anchoring on Algorand.
- A demonstrable end-to-end flow covering both the local-only pass and the escalated/paid path.

Excluded from MVP (see Future Scope):
- Multi-node / distributed Jetson deployments.
- Production-grade key management / HSM integration.
- General-purpose policy authoring UI.
- Real-time streaming verification.
- Broad language/query-dialect coverage beyond what is chosen for the demo (specific SQL dialect(s) TBD).

## 11. Future Scope

- Multi-agent / multi-tenant deployment with isolated policy sets per tenant.
- Richer semantic-repair provider marketplace (multiple providers competing for escalation calls).
- On-chain receipt verification smart contract/logic beyond simple Merkle anchoring.
- Formal policy language and policy versioning workflow.
- Expanded SQL dialect and query-safety rule coverage.
- Formal performance/latency/cost benchmarking against defined SLAs.

## 12. Optional Enhancements

- Local dashboard visualizing recent verification outcomes and audit anchoring status.
- Configurable repair-confidence thresholds for when to escalate vs. reject outright.
- Batch verification API for offline/bulk agent output review.

## 13. Success Criteria

- End-to-end demo executes both the free local-only path and the paid escalation path without manual intervention beyond providing input.
- A generated receipt can be shown to correspond to an anchored Merkle root on Algorand (i.e., audit integrity is demonstrably provable, not just asserted).
- A raw confidential payload is demonstrably never present in any on-chain transaction.
- At least one class of unsafe SQL and one class of schema-invalid output are shown being caught and either repaired or rejected.
- Judges can be shown the x402 HTTP 402 → `X-PAYMENT` → facilitator verification/settlement sequence concretely (e.g., via logs/trace), not just described.

## 14. Demo Scenario (Illustrative)

1. An AI agent produces a structured output (e.g., a function-call argument set or a SQL query) that is schema-valid but contains an unsafe SQL pattern.
2. Verified flags the issue locally; deterministic repair cannot safely resolve it (by design, unsafe SQL is not silently auto-rewritten — see THREAT_MODEL.md).
3. Agent produces a second output requiring a genuinely ambiguous field repair that *is* eligible for semantic escalation.
4. Verified returns HTTP 402; the agent's client presents `X-PAYMENT`; GoPlausible facilitator verifies/settles on Algorand.
5. Semantic-repair API returns a candidate fix; Verified re-validates it; it passes.
6. Verified issues a `verified (repaired)` receipt with hashes.
7. Operator triggers (or the system runs on schedule) a Merkle-root anchoring; operator shows the anchored root on an Algorand explorer and demonstrates that the local receipt hash is provably included, with no raw payload ever visible on-chain.
